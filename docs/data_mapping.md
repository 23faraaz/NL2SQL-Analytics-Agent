# Source-to-Target Data Mapping

This document records, for every populated column in the canonical `commerce`
schema, where its value comes from and how it was classified. Every column is
one of:

- **REAL** — an unmodified value from the real Olist dataset.
- **DERIVED** — computed deterministically from real data (a crosswalk, an
  aggregation, a formatted string built from a real identifier). Never
  fabricated; always traceable back to a real input.
- **SYNTHETIC** — generated by the S4b augmentation step (`etl/augment/`)
  because no real Olist data exists for it. Always deterministic for a given
  `ETL_AUGMENTATION_SEED`, never a guess presented as fact.
- **DEFAULT** — left unset, so the column's schema `DEFAULT` (or `NULL`, for
  nullable columns) applies.

Produced by, and kept in sync with, `etl/transform/*.py` (S4a) and
`etl/augment/*.py` (S4b).

## commerce.customers

| Column | Classification | Source / Rule |
|---|---|---|
| customer_id | DERIVED | Sequential, assigned during transform |
| first_name | SYNTHETIC | `etl/augment/customers.py`, seeded Faker |
| last_name | SYNTHETIC | seeded Faker |
| email | SYNTHETIC | `first_name.last_name.row@example.com`, guaranteed unique |
| phone | SYNTHETIC | seeded Faker |
| address_line_1 | SYNTHETIC | seeded Faker street address |
| address_line_2 | DEFAULT | left NULL (nullable, not on the approved synthetic list) |
| city | REAL | Olist `customer_city` |
| region | REAL | Olist `customer_state` (a Brazilian state code) |
| postcode | REAL | Olist `customer_zip_code_prefix` |
| country | DERIVED | fixed `'Brazil'` — real geography preserved, not overwritten to a UK default |
| acquisition_channel | SYNTHETIC | seeded random choice from the schema's CHECK-constrained enum |
| marketing_consent | DEFAULT | schema default `FALSE` |
| date_of_birth | DEFAULT | left NULL (nullable, not on the approved synthetic list) |

## commerce.suppliers

| Column | Classification | Source / Rule |
|---|---|---|
| supplier_id | DERIVED | Sequential, assigned during transform |
| supplier_name | DERIVED | `'Supplier ' + source seller_id` — a deterministic, traceable placeholder, never a fabricated company name |
| contact_name / contact_email / contact_phone | DEFAULT | left NULL (Olist has no seller contact data) |
| country | DERIVED | fixed `'Brazil'`; Olist's real `seller_city`/`seller_state` have no home in this table's single country column and are not retained |
| lead_time_days | DEFAULT | schema default `14` |
| active | DEFAULT | schema default `TRUE` |

## commerce.products

| Column | Classification | Source / Rule |
|---|---|---|
| product_id | DERIVED | Sequential, assigned during transform |
| category_id | REAL | resolved via the categories lookup |
| supplier_id | DEFAULT | left NULL — Olist's real seller assignment is per order line item (transactional), while this column is a single catalogue-level relationship; forcing a one-to-one link from many-to-many real data would misrepresent it |
| product_name | SYNTHETIC | `etl/augment/products.py`: real category name + two seeded Faker words |
| brand | SYNTHETIC | seeded random choice from a fixed house-brand list |
| description / material | DEFAULT | left NULL |
| launch_date | SYNTHETIC (real-anchored) | seeded random date before the dataset's real earliest order date; never after a product's first real sale |
| active | DEFAULT | schema default `TRUE` |

Real Olist `product_length_cm`/`height_cm`/`width_cm` have **no target column
anywhere in the canonical schema** (neither `products` nor
`product_variants` represents physical dimensions beyond weight) and are
not carried through at all — a documented loss of real data the schema has
no place for, not an omission. Real `product_weight_g` is retained
internally through the pipeline solely to derive `product_variants
.weight_grams` below; it is not itself a `commerce.products` column.

## commerce.product_variants (entirely new; no equivalent in any prior schema)

| Column | Classification | Source / Rule |
|---|---|---|
| variant_id | DERIVED | Sequential, assigned during generation |
| product_id | REAL | the real product this variant belongs to |
| sku | SYNTHETIC | deterministic, built from product_id + colour + size |
| colour / size | SYNTHETIC | seeded random choice from fixed vocabularies |
| unit_cost | DERIVED where possible, else SYNTHETIC | for a product with real order_items, a seeded random 35-65% of that product's real average sale price; products with no observed real sale fall back to a SYNTHETIC range (`etl/augment/product_variants.py`) |
| retail_price | DERIVED | `unit_cost × seeded random markup (1.4-2.5x)`, which trivially satisfies `retail_price >= unit_cost` |
| weight_grams | DERIVED | copied directly from the product's real Olist weight |

## commerce.orders

| Column | Classification | Source / Rule |
|---|---|---|
| order_id | DERIVED | Sequential, assigned during transform |
| customer_id | REAL | resolved via the customers lookup |
| discount_code_id / campaign_id | DEFAULT | left NULL (Future-phase entities, no data populated yet) |
| order_number | DERIVED | `'ORD-' + source order_id` |
| order_date | REAL | Olist `order_purchase_timestamp` |
| status | DERIVED | crosswalked from Olist `order_status` via `ORDER_STATUS_MAP` (`etl/config.py`) |
| sales_channel | DERIVED | fixed `'MARKETPLACE'` — a real, documented fact about Olist's own business model, applied uniformly, not a per-row guess |
| shipping_city / shipping_region / shipping_postcode | REAL | copied from the linked customer's real geography |
| shipping_country | DERIVED | fixed `'Brazil'`, same rationale as customers.country |
| subtotal | DERIVED | sum of this order's real `order_items.line_revenue` |
| discount_amount | DEFAULT | schema default `0` (Olist has no discount concept) |
| shipping_cost | DERIVED | sum of this order's real per-item freight (`freight_value_gbp`); commerce.order_items has no freight column of its own |
| tax_amount | DEFAULT | schema default `0` (Olist has no tax concept) |
| total_amount | DERIVED | `subtotal + shipping_cost` |
| currency | DEFAULT | schema default `'GBP'` (existing `BRL_TO_GBP_RATE` conversion applied to all monetary REAL/DERIVED fields) |

**Status crosswalk** (`ORDER_STATUS_MAP`): `delivered→DELIVERED`,
`shipped→SHIPPED`, `canceled→CANCELLED`, `processing→PROCESSING`,
`approved→PAID`, `invoiced→PAID`, `created→PENDING`,
`unavailable→CANCELLED` (weakest link — the closest real semantic match
among the target enum, not a perfect equivalence). `PARTIALLY_REFUNDED`/
`REFUNDED` are never produced (no Olist source concept; refunds are a
Future-phase entity with zero rows currently).

## commerce.order_items

| Column | Classification | Source / Rule |
|---|---|---|
| order_item_id | DERIVED | Sequential, assigned after consolidation |
| order_id | REAL | resolved via the orders lookup |
| variant_id | DERIVED | deterministic selection ((order_id + product_id) modulo the product's variant count) among the S4b-generated variants for the real product; every real row for the same (order, product) resolves to the same variant, then rows are consolidated to satisfy `UNIQUE(order_id, variant_id)` — see `etl/augment/order_items.py` |
| quantity | DERIVED | count of real Olist rows consolidated into this line (each real row is one unit; Olist has no quantity column) |
| unit_sale_price | REAL | Olist `price`, BRL→GBP converted (existing `BRL_TO_GBP_RATE`) |
| unit_cost_at_sale | DERIVED | copied from the resolved variant's `unit_cost` |
| line_discount | DEFAULT | schema default `0` (Olist has no per-item discount concept) |
| line_revenue | DERIVED | sum of the consolidated real rows' revenue |
| line_cost | DERIVED | `quantity × unit_cost_at_sale` |
| line_profit | DERIVED | `line_revenue − line_cost` |

## commerce.payments

| Column | Classification | Source / Rule |
|---|---|---|
| payment_id | DERIVED | Sequential, assigned during transform |
| order_id | REAL | resolved via the orders lookup |
| payment_reference | DERIVED | `source order_id + '-' + payment_sequential` (a real natural key in Olist) |
| payment_method | DERIVED | crosswalked from Olist `payment_type` via `PAYMENT_METHOD_MAP` (`credit_card`/`debit_card→CARD`, `boleto→BANK_TRANSFER`, `voucher→GIFT_CARD`, `not_defined→CARD` fallback) |
| payment_status | DERIVED | `SUCCESSFUL` unless the linked order's real status is `CANCELLED`, in which case `FAILED` |
| amount | REAL | Olist `payment_value`, BRL→GBP converted |
| payment_date | DERIVED | copied from the linked order's real `order_date` (Olist payments carry no date of their own) |

## Not populated in this milestone (schema already supports them; no rows yet)

`customer_segments`, `customer_segment_memberships`, `campaigns`,
`discount_codes`, `refunds`, `refund_items`, `inventory_movements` — these
tables exist (created by `sql/001_schema.sql`) but have zero rows. Every
view that joins against them (`order_financials`, `customer_lifetime_metrics`,
etc.) does so via `LEFT JOIN` with `COALESCE(...,0)`, so they degrade
gracefully to zero rather than breaking. Populating them is explicitly
future-phase work per the agreed roadmap.
